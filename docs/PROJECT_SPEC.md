# RelayPulse 项目总方案

> 当前实施阶段：[MVP 01：桌面壳与 UI](./01-relaypulse-desktop/README.md)

## 1. 产品定位

RelayPulse 是一款运行在 macOS、Windows 和 Linux 桌面环境中的 AI 模型可用性探针。它常驻系统托盘，按设定频率向用户选中的模型发送最小化真实生成请求，并把最新状态直接显示在托盘图标和轻量状态面板中。

RelayPulse 不是站点 Ping 工具。只有协议解析器收到有效模型输出并通过校验，探针才算成功，从而区分“站点能够连接”和“模型能够实际生成内容”。

- `Relay`：AI API 中转站、代理站点或模型服务
- `Pulse`：周期性真实请求、实时状态与响应速度

## 2. 用户结果

用户配置站点、凭据和需要监控的模型后，无需一直打开主窗口，即可通过系统托盘获得以下信息：

1. 所有已启用模型的整体健康状态。
2. 全部正常时显示有效站点、有效模型数量和探测时间摘要。
3. 存在异常时显示按站点优先级排序的最多 3 个异常模型、站点名称、首 Token 耗时和总耗时；不可测量时显示明确短语。
4. 在需要时手动发起探测或进入配置主窗口。

主窗口只负责管理配置，不承担仪表盘、趋势分析或大屏监控职责。

## 3. 产品原则

1. **托盘优先**：托盘图标和状态面板是主要使用入口，配置窗口是辅助入口。
2. **真实探测**：发送真实生成请求并解析实际响应，不用网络连通性代替模型可用性。
3. **指标可信**：流式请求分别记录响应头时间、TTFT 和总耗时；非流式响应不得伪装成 TTFT。
4. **低干扰**：请求短、Token 消耗低、调度错峰，避免不必要费用和集中请求。
5. **跨平台核心一致**：协议、调度、状态和存储语义在三平台一致，仅系统集成通过适配层区分。
6. **Secret 不落明文**：API Key 进入系统凭据库，日志、诊断和导出内容统一脱敏。
7. **MVP 克制**：第一版不提供图表、复杂统计、云端服务或完整 API 调试功能。

## 4. 支持平台与交互差异

目标平台为：

- macOS 桌面
- Windows 桌面
- Linux 桌面，首批发行版和桌面环境在 MVP 开发前通过能力验证确定

统一交互契约：

- 托盘图标使用红、黄、绿表达整体状态。
- 全部正常时状态面板只显示整体摘要；存在异常时最多显示 3 个异常模型及 TTFT、总耗时或错误短语。
- macOS 和 Windows 优先支持悬停显示、移出延迟关闭，单击可固定面板。
- Linux 不强求悬停一致性，允许使用单击或原生托盘菜单打开状态面板。
- 三个平台的面板内容、状态含义和配置能力保持一致，触发方式允许因系统能力不同而变化。

## 5. 核心概念

### 5.1 站点 `Site`

一个站点代表一个 AI API 中转站或模型服务，至少包含：

- 站点名称与 Base URL
- 协议适配器类型
- 模型列表 Method 与 Endpoint
- 探针 Method 与 Endpoint
- API Key 的系统凭据引用
- 鉴权预设和自定义 Header 模板
- 探测频率、超时、状态阈值及启用状态
- 用户可拖动的站点优先级
- 默认探针策略，包括推理模式、最大输出和固定提示词

站点只有在自身已启用且至少一个模型已启用时才参与调度、计数和状态聚合。已启用但没有启用模型的站点保留配置，并明确显示为“不参与探测”。

### 5.2 模型 `Model`

模型可以自动发现、手动添加或混合管理，至少包含：

- 模型标识符与可选展示名称
- 所属站点
- 来源：`discovered` 或 `manual`
- 发现状态
- 是否启用监控
- 自动识别或手动指定的推理能力
- 可继承站点默认值的探针策略覆盖
- 受限透传参数
- 最近一次稳定状态及探测摘要

自动刷新模型列表时保留已有启用状态和历史。服务端暂时不再返回某模型时，标记为“未发现”，不立即删除本地记录。

### 5.3 探针 `Probe`

一次探针是向指定模型发出的最小化真实请求：

- 默认使用流式响应。
- 默认要求简短、可验证的固定输出，例如 `PROBE_OK`。
- 不携带用户业务数据。
- 具备响应头、首 Token 和总请求三层超时。
- 同一模型不允许出现重叠探测。

### 5.4 最新状态 `ModelStatus`

每个已启用模型都有一份可直接投影到托盘面板的最新状态。SQLite 中的配置和探测结果是权威数据；内存状态用于调度和即时推送，进程重启后可由数据库重建。

## 6. 托盘与界面契约

### 6.1 托盘图标

托盘图标反映所有已启用模型中的最高严重级别：

| 颜色 | 整体含义 |
|---|---|
| 绿色 | 所有已取得结果的模型均健康，且没有等待首次结果的模型 |
| 黄色 | 至少存在慢速、正在探测、尚无结果或需要关注的模型，且没有红色故障 |
| 红色 | 至少一个模型处于确定故障状态 |

若没有启用任何模型，图标使用中性未配置状态，不伪装成健康。

### 6.2 状态面板

状态面板是产品的主要信息界面。它应轻量、紧凑、可快速扫描，不使用图表、营销说明、嵌套卡片或装饰性大标题。

状态面板只有两种主要信息状态：

- **全部正常**：不显示模型列表，只显示“全部正常”、有效站点/模型数量、最近完成时间和下一次探测时间。
- **存在异常**：显示异常总数，以及按站点优先级排序的最多 3 个异常模型。每条包含状态灯、模型名、站点名、首 Token 和总耗时；不可测量值使用“超时”“失败”或破折号，不伪造数字。

异常排序先使用站点优先级，再使用站点内稳定模型顺序。停用站点、没有启用模型的站点和停用模型不进入面板计数或异常列表。模型名和站点名空间不足时单行省略，并提供完整可访问名称。

面板可提供“立即探测”和“打开设置”图标操作，但不得放置配置表单、图表或长列表管理。没有有效模型时使用中性未配置状态，不显示“全部正常”。

### 6.3 配置主窗口

主窗口只负责：

- 新增、编辑、启用、停用和删除站点
- 拖动站点顺序并设置优先级
- 安全录入或替换 API Key
- 自动刷新、手动添加和选择监控模型
- 配置站点默认极省探针策略和单模型推理/透传参数
- 配置协议、Endpoint、Header、频率、超时和状态阈值
- 手动触发单模型、单站点或全部模型探测
- 查看必要的脱敏诊断信息
- 配置开机启动、关闭窗口后继续运行、托盘行为、主题、语言、历史保留和日志

主窗口不提供趋势图、P50/P95 图表或复杂历史分析。最终界面、`view` 命名和视觉验收基线见 [RelayPulse UI 定稿索引](./design/final/README.md)。操作系统原生窗口控制不由应用统一绘制。

## 7. 功能需求

### 7.1 站点与密钥管理

用户可以新增、编辑、启用、停用、删除和拖动排序多个站点，越靠上优先级越高。站点只有在已启用且至少一个模型已启用时才实际参与探测。API Key 必须保存在各平台系统凭据库中，SQLite 只保存不可反推出密钥的引用。Linux 凭据库不可用时必须给出明确阻塞或经确认的安全降级，禁止无提示明文保存。

### 7.2 模型发现与选择

支持自动获取、手动添加和混合模式。自动发现后不默认启用所有模型，避免对嵌入、图像、语音或大量别名模型产生无效请求及费用。

默认探针策略优先关闭模型思考；不支持关闭时使用最低推理，并限制最大输出和固定提示词。单模型可覆盖策略并增加受限透传参数，但不得覆盖 `model`、`messages`、`stream`、鉴权或内部追踪字段。界面中的有效请求预览必须与实际发送的非 Secret 字段一致。

### 7.3 探测频率与调度

站点级频率至少支持关闭自动探测、10、20、30、60 分钟及自定义分钟数。调度器还应支持：

- 应用启动后按配置执行一次探测
- 手动立即探测单模型、单站点或全部模型
- 少量随机错峰
- 系统唤醒后重新计算下一次任务，不补发全部遗漏任务
- 网络恢复后允许重新探测
- 防止同一模型的周期任务重叠
- 应用退出后停止探测，MVP 不运行独立守护进程

### 7.4 协议与 Endpoint

核心逻辑通过 `ProbeAdapter` 隔离服务格式：

```text
ProbeAdapter
  - fetchModels(siteConfig)
  - buildProbeRequest(siteConfig, model)
  - parseStreamEvent(data)
  - validateResponse(result)
  - normalizeError(response)
```

MVP 支持 OpenAI Compatible 和受限 Custom HTTP。站点可分别配置模型列表与探针的 Method、Endpoint、Content-Type、流式开关及超时。Endpoint 可以是相对 Base URL 的路径或完整 URL；完整 URL 不继承 Base URL，并必须在界面明确提示。

### 7.5 自定义鉴权与校验

鉴权预设至少包含：

```text
Authorization: Bearer {{apiKey}}
x-api-key: {{apiKey}}
api-key: {{apiKey}}
```

支持多个自定义 Header，模板变量第一版限定为 `{{apiKey}}` 和 `{{model}}`。Header 名称必须校验，敏感 Header 值不得进入日志、历史或错误报告。

Custom HTTP 的声明式校验至少覆盖：

- HTTP 状态码属于成功范围
- 响应正文包含指定文本
- JSON 指定路径存在或等于预期值
- 流式响应至少产生一次有效内容事件

MVP 不执行用户提供的 JavaScript、Shell 或正则脚本。

## 8. 指标定义

### 8.1 流式请求

```text
T0：请求开始
T1：收到 HTTP 响应头
T2：协议解析器确认第一段有效模型输出
T3：收到正常流结束标记或连接正常结束
```

- 响应头时间：`T1 - T0`
- 首 Token 时间（TTFT）：`T2 - T0`
- 总耗时：`T3 - T0`
- 输出阶段耗时：`T3 - T2`

SSE 心跳、注释、空增量、角色字段和元数据不能作为 T2。

### 8.2 非流式请求

非流式接口只记录响应头时间和完整响应时间。TTFT 必须为空，并明确标记为该请求不可测量，禁止用完整响应时间冒充 TTFT。

### 8.3 探针记录

每次探针至少记录站点、模型、开始/结束时间、状态、HTTP 状态码、标准化错误、各阶段耗时、服务端报告模型、完成原因、可获得的 Token 用量、是否正常结束和重试次数。

不保存完整请求正文和完整模型回答，只允许保存有限长度且已脱敏的诊断摘要。

## 9. 状态与错误分类

内部状态至少包含：

- `healthy`
- `slow`
- `probing`
- `rate_limited`
- `auth_error`
- `model_unavailable`
- `timeout`
- `protocol_error`
- `validation_failed`
- `upstream_error`
- `network_error`
- `paused`
- `unknown`

面板颜色映射：`healthy` 为绿色；`slow`、`probing`、`unknown` 为黄色；各类确定失败为红色；`paused` 不进入已启用模型列表。

状态切换支持连续失败和恢复阈值，避免单次抖动导致颜色频繁变化。默认阈值在 MVP 实施前评审确认。

## 10. 数据与安全

SQLite 保存站点非敏感配置、模型、探针结果和最新状态投影。系统凭据库保存 API Key。核心实体为：

```text
Site
Model
ProbePolicy
ProbeResult
LatestModelStatus
GeneralSettings
```

删除站点时必须明确提示，并在事务中删除其模型、历史记录和对应凭据；失败不得留下“数据库已删但密钥仍在”或相反的无说明状态。MVP 不提供云同步和多设备共享。

所有 URL、Header、响应摘要和错误在进入日志前经过统一脱敏。日志不得包含 API Key、完整 Authorization 值、用户业务正文或第三方完整原始响应。

## 11. 技术架构与实施层级

完整产品仍采用 Tauri 2 + Rust + React/TypeScript。实施顺序固定为：

1. **MVP 01 桌面壳与 UI**：建立 Tauri/Rust 壳、托盘和窗口生命周期，使用 React、TypeScript、Vite、Ant Design 与类型化 mock data source 实现并验收九个定稿 view。
2. **后端数据层**：在已验收 UI 接口后实现 SQLite、migration、系统凭据库和真实配置重建。
3. **探针与状态层**：实现 Tokio/Reqwest 流式请求、协议适配、TTFT/总耗时、调度和状态聚合，再通过 Tauri adapter 接入现有 UI。
4. **发行层**：完成三平台签名、公证、安装、升级和完整纵向验收。

MVP 01 不安装或实现 SQLx、SQLite、CredentialStore、Reqwest、真实协议解析和调度器。UI 只依赖稳定的 `RelayPulseDataSource` 接口，后端通过 adapter 接入，不允许页面组件直接访问数据库、Secret 或模型 API。

模块边界：

```text
Desktop Shell
  - Tray Icon
  - Status Panel Window
  - Configuration Window

Probe Core
  - Scheduler
  - Probe Executor
  - Status Aggregator
  - Timeout / Retry / Cancellation

Protocol Adapters
  - OpenAI Compatible
  - Custom HTTP

Persistence & Security
  - SQLite Repositories / Migrations
  - CredentialStore
  - Redaction

Platform Integration
  - Tray Behavior
  - Power / Network Events
  - Autostart and Packaging
```

Rust 核心不得依赖前端窗口生命周期；关闭配置窗口或状态面板不能停止调度。平台差异通过明确适配器收敛，不允许散落在协议和状态逻辑中。

## 12. 完整产品范围与阶段归属

完整桌面产品包含：

1. macOS、Windows、Linux 桌面应用及托盘入口。
2. 多站点、系统凭据库和模型选择。
3. OpenAI Compatible 模型发现与流式真实探针。
4. 受限 Custom HTTP、Endpoint、Header 和声明式校验。
5. 站点级周期调度、手动探测、错峰、防重叠和唤醒恢复。
6. 可信 TTFT、总耗时、最新状态及有限历史记录。
7. 红黄绿托盘图标、全部正常摘要和最多 3 条异常的紧凑状态面板。
8. 符合九张定稿图、只用于配置与必要诊断的主窗口。
9. 三平台安装制品与最小支持范围说明。

其中 MVP 01 只交付第 1、7、8 项的桌面壳、视觉与 mock 交互，以及后端接入所需的 UI data source 契约。第 2 至 6 项和真实状态驱动在后端阶段实施，第 9 项的正式签名发行在发行阶段实施。

完整产品不包含：

- 图表、趋势分析和 P50/P95 界面
- 回答质量评分
- 大规模并发压测
- 云端监控、账户系统和多设备同步
- 独立守护进程
- Webhook 和系统告警
- 任意脚本式请求、鉴权或校验逻辑
- Anthropic、Gemini 专用适配器

## 13. 后续方向

后续阶段可以基于现有适配器、状态与持久化契约增加：

- Anthropic 和 Gemini 专用适配器
- 配置导入导出，不包含密钥
- 系统通知与 Webhook
- 模型级独立频率和阈值
- 用户确认确有需求后的历史聚合或趋势能力

这些能力不得提前扩大当前 UI 阶段或完整产品首发范围。

## 14. 项目级验收原则

MVP 01 必须在每个声明支持的平台上证明：Tauri 壳可构建启动、托盘和窗口生命周期成立、九个定稿 view 与主要 mock 交互可用、UI 只依赖稳定 data source 且没有提前混入后端实现。

完整产品候选最终还必须证明：可安全保存凭据、可配置并探测真实兼容模型、可正确测量 TTFT、可分类主要故障、可持续调度，且托盘图标和状态面板与最新权威状态一致。这些不是 MVP 01 的验收门槛。

当前阶段的详细需求、任务、测试、验收场景和证据要求由唯一入口 [MVP 01：桌面壳与 UI](./01-relaypulse-desktop/README.md) 管理。
